# 协作流程稿

这份文档说明「工作怎么做、谁来做」：哪个模型规划、哪个复核、哪个施工，何时开新会话，怎样交接、验收和合并。要做什么、先后顺序和每一阶段的范围，写在 [规划方案](plan.md) 里。

读者主要是项目作者本人。流程本身不依赖具体项目，换一个项目也能照用。

---

## 一、三条原则

1. **一个会话只做一件事。** 会话窗口就是模型的工作记忆，每一步都要把全部历史重读一遍。规划、复核、施工、下一个阶段，各用一个新会话。
2. **交接只靠仓库。** 每个会话以仓库里的产出收尾：规划收尾于 `docs/plan.md`，施工收尾于 PR。下一个会话从这些产出开始，不依赖聊天记录。
3. **只在会话边界换模型。** 缓存不跨模型，中途换模型会让整段历史按全价重读一次，新模型还要背着上一个任务的全部历史。

---

## 二、角色

| 角色       | 做什么                                               | 产出                                  | 由谁担任                                            |
| ---------- | ---------------------------------------------------- | ------------------------------------- | --------------------------------------------------- |
| 规划       | 通读项目，诊断问题，设计方案，排阶段                 | `docs/plan.md`                        | 能力最强、额度稀缺的模型（目前是 fable）            |
| 复核       | 对照当前代码核实某一阶段的方案，列出遗漏和不成立之处 | 意见清单；经裁决后写回 `docs/plan.md` | 另一个模型（目前是 6a），新会话                     |
| 施工       | 实现一个阶段，跑测试，开 PR                          | 一个 PR                               | 成本较低的模型（目前是 6a），Devin 或 Codex，新会话 |
| 裁决与验收 | 决定分歧，亲手试用，点合并                           | 合并后的 `main`                       | 作者本人                                            |

模型的分工是作者当前的选择，可以随时调整；流程不变。

---

## 三、一个阶段的完整循环

| 步骤                                | 谁       | 在哪里      | 做什么                                                                       | 结束标志                   |
| ----------------------------------- | -------- | ----------- | ---------------------------------------------------------------------------- | -------------------------- |
| 1. 选阶段                           | 作者     | —           | 看 `docs/plan.md` 顶部的进度表，取下一个未开始的阶段                         | 确定阶段编号               |
| 2. 复核（高风险阶段必做，其余可选） | 复核模型 | 新会话      | 对照当前 `main` 核实该阶段的任务单                                           | 交出意见清单后停下         |
| 3. 裁决                             | 作者     | 复核会话    | 逐条决定采纳与否，让复核会话把结论写回 `docs/plan.md` 并开 PR，合并          | 文档已更新                 |
| 4. 施工                             | 施工模型 | 新会话      | 只实现这一个阶段                                                             | 开 PR 后停下               |
| 5. 自动检查                         | 施工会话 | 同一会话    | `npm run check`、相关窗口脚本、自动审查、实际操作录屏                        | PR 里写明结果              |
| 6. 验收                             | 作者     | 自己的电脑  | 按 PR 里的验收清单逐项试用（见第六部分）                                     | 全部符合，或列出不符合的项 |
| 7. 修改                             | 施工模型 | 原施工会话  | 修不符合的项，重新自动检查                                                   | 回到第 6 步                |
| 8. 更新文档                         | 施工会话 | 原施工会话  | 作者确认验收通过后，在同一个 PR 里更新 `docs/plan.md` 的进度、决定、遗留问题 | PR 已更新                  |
| 9. 合并                             | 作者     | GitHub 页面 | 点「Merge pull request」                                                     | PR 显示「Merged」          |
| 10. 收尾                            | 施工会话 | 原施工会话  | 把作者电脑上的代码切回 `main` 并重新构建                                     | 会话结束，不再派新任务     |

高风险阶段指会改工程文件格式或渲染管线的阶段：2a、2b、4b、5a、5b。这些阶段另加两件事：

- 开工前把 `作品` 文件夹复制一份作为备份。
- 合并前另开一个新会话，让规划模型只审这个 PR 的改动。

## 四、每种会话的第一条消息

第一条消息写清四件事：目标、范围、做到哪停、怎样算完成。把方括号里的内容换成实际值。

**规划**

> 请通读这个项目并 [审视的角度]，然后回答这些问题：[问题列表]。只做规划，不要改代码。把规划写成 docs/plan.md 并开 PR，然后停下。结论要标明哪些是实测、哪些是读代码推断。

**复核**

> 读 docs/plan.md 中阶段 [编号] 的任务单和它引用的章节，对照当前 main 的代码逐条核实。列出：与代码不符之处、遗漏、风险、不成立的假设。不要重写方案，不要改代码。交出清单后停下。

**施工**

> 按 docs/plan.md 实现阶段 [编号]（[名称]）。先读文档中对应章节，并对照当前 main 核实；有出入先告诉我，不要直接改方案。只做这一个阶段，开 PR 后停下。完成标准：`npm run check` 通过，相关 e2e 通过，附实际操作录屏，并在 PR 里给出我能亲手照做的验收清单。

**修改（在原施工会话里）**

> 验收清单第 [几] 项不符合：我做了 [操作]，看到的是 [现象]，应该是 [预期]。请修复并重新检查，更新 PR 后停下。

**高风险阶段的审查**

> 审查 PR #[编号] 的改动，对照 docs/plan.md 中阶段 [编号] 的任务单。重点看：旧工程打开后行为是否不变、数据迁移是否完整、撤销和保存重开是否正确。只列问题，不要改代码。

**合并后才发现的问题**

> main 上 [功能] 有问题：我做了 [操作]，看到的是 [现象]，应该是 [预期]。这个功能来自 PR #[编号]。请定位并修复，开 PR 后停下。

## 五、何时开新会话

**开新会话**

- 任务性质变了：规划转复核、复核转施工、一个阶段转下一个阶段。
- 当前任务已经交付（PR 已合并）。
- 准备问一个与当前任务无关的问题。
- 模型忘了早先的要求，或前后说法矛盾。
- 要换模型。

**留在原会话**

- 修同一个 PR 的问题。
- 对刚完成的工作做小修改。
- 追问刚才的结论。

**长时间等待之后**：空闲较久，缓存多半已失效。这时开新会话或换模型几乎没有额外损失。

## 六、验收与合并（不需要读代码）

PR（Pull Request）是一份「待批准的改动」。新代码放在单独的分支上，不影响正式版本 `main`；合并之后改动才进入 `main`。不合并，`main` 保持原样。

**验收看三样东西**

1. PR 页面里的验收清单：每一项是「做什么操作、应该看到什么」。
2. PR 页面里的录屏：施工会话实际操作的过程。
3. 自己电脑上的新版编辑器：照清单逐项试。前两样不能代替这一项，施工会话的机器没有独立显卡，流畅度和闪烁只有在自己的电脑上才能确认。

**在自己电脑上打开新版**

`启动编辑器.cmd` 运行的是已经构建好的文件，所以只切换代码还不够，必须重新构建。先保存工程并关闭编辑器，然后二选一：

- 让 Devin 来做：对施工会话说「请连接我的电脑，把 `桌面\音游编辑器` 切到这个 PR 的版本并构建」，在弹出的提示里批准。
- 自己做：在 `桌面\音游编辑器` 文件夹里打开 Git Bash，依次运行：

  ```sh
  git fetch origin
  git checkout [PR 页面标题下方显示的分支名]
  npm.cmd run build
  ```

  如果构建时提示缺少依赖，先运行 `npm.cmd install` 再构建。

然后双击 `启动编辑器.cmd`。

**验收结果**

- 全部符合：告诉施工会话「验收通过」，等它把 `docs/plan.md` 的进度更新进同一个 PR，然后合并。
- 有不符合的项：回到原施工会话，用第四部分的「修改」模板描述现象。不需要判断原因。
- 清单之外发现的问题：同样告诉施工会话，由它判断是这次引入的还是原来就有的。

**合并**

1. 打开 PR 页面，滚到最下方。
2. 点绿色按钮「Merge pull request」，再点「Confirm merge」。
3. 页面标题下方的标签变成紫色的「Merged」即完成。没有变化就刷新页面。

合并必须由作者本人点，Devin 的合并操作会被安全检查拦下。

**合并之后**

让施工会话把电脑上的代码切回 `main` 并构建，或自己运行：

```sh
git checkout main
git pull
npm.cmd run build
```

## 七、用 Devin 以外的工具施工时

- 外部工具读不到 Devin 的会话和附件。规划文档、分支、验收标准都必须已经在仓库里。
- 开工前确认它能运行 `npm.cmd run check`。它启动不了编辑器窗口时，窗口脚本和录屏交给 Devin 的新会话或在自己电脑上完成，不能省略。
- 同一个分支同一时间只让一个工具改。
- 指令要更具体：涉及哪些文件、数据结构怎么改、要通过哪些测试、做到哪停。可以先让复核会话把这些写进任务单。
- 使用第三方渠道时，实际提供的模型、稳定性和代码经手方都无法由作者核实；高风险阶段不建议使用。

## 八、小词典

| 词              | 意思                                                                    |
| --------------- | ----------------------------------------------------------------------- |
| 仓库            | 存放项目全部代码和文档及其修改历史的地方，这里指 GitHub 上的 `colortap` |
| `main`          | 正式版本。合并进来的改动才算数                                          |
| 分支            | 从 `main` 分出来的一份副本，在上面改动不影响 `main`                     |
| PR              | 请求把一个分支的改动合并进 `main`，附带说明、检查结果和讨论             |
| 合并            | 批准 PR，改动进入 `main`                                                |
| 构建            | 把源代码转换成编辑器实际运行的文件（`out` 文件夹）                      |
| `npm run check` | 一次跑完类型检查、单元测试和构建                                        |
| 窗口脚本（e2e） | 自动打开编辑器、模拟操作并核对结果的脚本，在 `scripts/` 里              |
| 上下文          | 模型在一个会话里要读的全部内容；越长越慢、越贵、越容易遗漏              |
| 缓存            | 模型对已读过的相同开头按折扣价读取；换模型或空闲过久会失效              |
