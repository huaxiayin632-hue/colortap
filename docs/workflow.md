# 协作流程

本文件约定怎样推进、对齐和验收。当前目标、顺序及决定集中在 [规划方案](plan.md)；具体改动和验证结果放在对应 PR。2026-11-20 按糖糖确认的方式修订。

## 一、职责与边界

- **糖糖决定产品取舍**：目标、优先级、使用手感、视觉效果、阶段范围，以及需要保留哪些作品或数据。每个阶段完成后停下对齐。
- **执行者负责技术落地**：核实代码、选择实现方式、处理普通技术问题、修复测试、准备可试用版本，说明结果与限制。已批准范围内的日常实现不必逐项请示。
- **独立审查负责发现遗漏**：高风险改动在交付验收前由独立会话审查，重点看行为是否正确、保存是否可靠、检查是否充分。模型分工按任务需要选择，不固定在某几个型号。
- **需要改变约定时再对齐**：发现方案与现状不符，执行者先判断影响；普通技术调整自行处理并报告，影响产品行为、范围或数据保留的变化带着具体方案交给糖糖决定。

当前已确认：现存旧工程可忽略，不必为它们实现兼容与迁移。这不取消新建工程的保存、恢复和重开要求。

## 二、一个阶段的推进

| 步骤 | 执行者负责 | 糖糖参与 |
| --- | --- | --- |
| 1. 确定本次成果 | 从当前计划提取目标、范围和完成条件；核对代码与环境 | 决定目标和必要的产品取舍 |
| 2. 实现与验证 | 在独立分支实现；检查、修复；必要时接受独立审查 | 普通技术细节无需逐条裁决 |
| 3. 交付 | 整理 PR、可试用版本和简短操作清单，附适用的测试与录屏；完成后停下 | 在本机试用，反馈手感、效果和不符合之处 |
| 4. 修正与验收 | 在原会话修复，重跑受影响的检查，更新同一 PR | 确认结果达到本阶段目标 |
| 5. 合并与收尾 | 根据合并结果更新计划、准备本机正式版本，清退无用临时产物 | 决定合并；阶段结束后对齐下一步 |

普通方案调整写入同一份计划，可随实现放在同一个 PR 中。纯规划任务直接交付文档与待决定事项，不为每条复核意见再开一个文档 PR。

**高风险按改动内容判断**：渲染管线、工程写入/恢复、时间与判定规则、镜头坐标及数据结构变化，都应针对主要风险作独立审查。审查不要求由最初规划者担任，也不重复整份项目调查。

需要保护的工程，使用副本试验，连同引用素材一起保留。现存已明确放弃的旧工程不作为迁移工作；后续开始积累的新作品若受格式变化影响，先明确保留方式。

## 三、会话怎样划分

本项目当前约定：讨论窗口用于规划、取舍与阶段性对齐，可更新规划和流程文档；程序执行另开窗口。执行窗口每次完成一个已确定阶段，交付后停下，下一阶段由糖糖对齐后安排。

执行窗口围绕一个连贯成果。已批准范围内的方案细化、实现、测试、验收修复和结论追问可以留在同一会话，角色变化本身不要求重开。

独立审查、与当前工作无关的新目标，或已经明显偏离任务的会话，适合开新会话。上一阶段交付后，根据下一阶段与已有上下文的关系选择是否继续；无论是否新开，都在阶段结束时停下对齐。

按任务需要选择模型，不以「一换模型就必须开新会话」或「等待较久就必须重开」作为流程规则，也不根据未经核实的缓存计费推断安排工作。

交接时只需要让接手者从仓库和 PR 找到：本次目标、最新决定、工作版本、验证结果和剩余问题。重要结论及时写回已有记录，不要求接手者重读全部聊天，也不另写一套重复交接文档。

## 四、交付与验收

执行者交付时说明：

- **改了什么、怎样试**：每一项写成「操作 → 预期结果」，优先覆盖本次真正变化的体验。
- **验证了什么**：检查命令、结果、代码版本和必要的环境信息；区分已验证、未验证及受限项目。
- **证据在哪里**：界面、交互和动画变化提供必要录屏；纯逻辑变化以对应测试为主；纯文档修改检查内容、链接和格式，无需强制录屏。

代码改动通常运行 `npm.cmd run check`（类型检查、单元测试、构建）及相关窗口脚本。检查通过后，不因重复汇报而重跑无关测试；改动或失败产生新的验证需要时再运行。

性能与操作手感在糖糖的实际机器上核对。执行者能在本机运行时直接准备证据；如果当前环境无法运行窗口，则明确缺口并安排可运行环境验证。录屏和自动检查帮助验收，实际试用决定手感是否合适。

**版本必须对应**：PR 的改动版本、自动检查、录屏和本机试用版本要说得清楚。验收后若程序又改动，重新验证受影响部分；只更新计划状态不用重复验收程序。计划中区分「待验收」「验收通过待合并」「已合并」，合并后才标记已合并。

不符合时，糖糖描述操作与现象即可，例如：

> 我拖动图层后，图像闪了一下；预期是连续跟着鼠标移动。请定位并修复，更新原 PR 后停下。

清单之外的问题也可以提出；执行者判断它是本次引入的问题还是另一项任务，不把所有新想法塞进正在验收的改动。

## 五、本机试用、合并与收尾

`启动编辑器.cmd` 运行的是构建产物。准备新版时，执行者先检查当前分支及未提交改动，保护已有工作；保存并关闭编辑器后，准备指定 PR 的代码和依赖，再构建。必要时用隔离的工作目录，避免影响正在使用的版本。

糖糖可以直接说：

> 请准备这个 PR 的本机试用版本，核对实际运行的版本，给我一份简短的操作清单。

**合并由糖糖决定**：可以本人操作，也可以明确授权工具执行。不能把某个平台曾经拒绝合并，写成所有工具永久适用的规则。

合并后，执行者按实际工作目录更新正式代码、依赖和构建产物，确认启动器运行的是目标版本。保留必要成果与验证证据，清理本次不再需要的临时产物；不清理他人的未完成工作。

## 六、简短任务模板

**规划或复核**

> 阅读 docs/plan.md 中 [阶段] 及相关代码，核实范围与关键假设。普通技术问题给出建议处理方式；影响产品行为或范围的事项集中说明。只做评估，不改程序；完成后停下。

**实现**

> 按 docs/plan.md 完成 [阶段/成果]。先核对当前代码，普通技术细节自行处理并说明；涉及产品行为、范围或数据保留的变化再与我对齐。完成实现和相关验证，提交 PR 与本机验收清单后停下。界面变化附必要录屏。

**独立审查**

> 审查 PR #[编号]，对照当前已确认目标。重点检查本次改动的行为、时间与坐标规则、撤销、素材引用和保存重开；按现行决定判断兼容范围。列出具体问题和影响，不直接改程序。

## 七、换工具时

- 开工前核实代码、目标版本、运行与测试能力；不要假设某个工具必然能或不能访问某个附件。
- 同一分支同一时间只由一个执行者修改；需要并行工作时使用独立分支和工作目录。
- 接手信息以当前计划和 PR 为准；已有结论不反复让糖糖重新决定。
- 无法完成的验证明确说明，由具备相应能力的环境完成，不写成已经通过。

## 八、小词典

| 词 | 含义 |
| --- | --- |
| 仓库 | 项目的代码、文档及修改历史 |
| main | 合并后使用的正式代码分支 |
| 分支 / PR | 隔离一项改动，并集中查看、讨论和批准它 |
| 构建 | 将源代码转成启动器运行的文件 |
| 窗口脚本（e2e） | 自动打开编辑器、操作界面并核对结果 |
